## §1 Purpose and scope of G0

G0 is the acquisition gate. It answers one question: **can we capture the
frozen corpus from two independent sources, immutably, with auditable
provenance?** G0 builds no normalization, no universe logic, no query layer,
no UI, no orchestrator, no database platform. It acquires.

The first profile is `es-corporate-bonds`. The two G0 sources are:

| source_id | display          | kind                       | publication format |
|-----------|------------------|----------------------------|--------------------|
| bme_apa   | BME APA          | post-trade transparency    | JSON                |
| blb_apae  | Bloomberg APAE   | delayed trade reports      | provider-defined    |

Canonical entrypoints, access mode, and per-source retrieval intervals are
defined in `config/sources/{bme_apa,bloomberg_apae}.yaml`. The spec freezes
BEHAVIOR, not bytes; the interface points to config and MUST NOT hard-code
source URLs.

## §2 G0-A — Acquisition engine (smoke + capture)

`G0-A` freezes the acquisition behavior common to all sources.

### G0-A.1 Capture pipeline (per source, one responsibility each)

A collector is a chain with one responsibility per stage:

1. **discover/fetch** — resolve the source retrieval target and obtain the
   exact source object (response bytes / file bytes).
2. **capture** — persist the exact bytes, write-once, unchanged.
3. **derive capture metadata** — observe the identity, timestamps, and
   provenance required below.
4. **write immutable raw object** — persist to the local raw directory.
5. **record metadata** — persist `raw_sha256` + observation metadata in the
   evidence manifest.

A source adapter MUST NOT normalize trades. Source-specific quirks stay inside
the adapter; they MUST NOT leak into a premature universal model. The output of
G0-A1 is a captured raw object plus provenance metadata, not a normalized trade.

### G0-A.2 Raw object identity

Raw object identity is the tuple of source-defined fields that make a
publication unique for that source. It is defined per source in
`config/sources/*.yaml`. Capture identity is the minimum required to store an
object and to answer "is this the same object again?" — but it NEVER performs
economic, fuzzy, or heuristic deduplication. That is G0-D territory.

### G0-A.3 Immutability and write-once

- Captured raw files are write-once. Never overwrite an existing raw object.
- `raw_sha256` is computed from the exact captured bytes and recorded at capture.
- If the same source object is encountered again, follow the capture-identity
  rule: the object is either a new publication (new file) or an already-captured
  object (no state change). Never modify the original file.
- Re-runs MUST NOT alter existing raw objects. (Second ingest idempotence is
  verified by `SECOND_RUN_IDEMPOTENT`, §2 G0-A.7.)

### G0-A.4 Timestamps

- Record the observation/retrieval time of each capture (UTC, ISO-8601).
- Record the source publication timestamp per the per-source publication
  timestamp semantics defined in `config/sources/*.yaml`.
- Daily rescan keys on `publication_timestamp` and rescans the previous 24h.
- A 7-day rolling rescan must be available and operating.
- Source-specific retrieval intervals are in `config/sources/*.yaml`. The spec
  does not substitute a generic temporal model for a source's own.

### G0-A.5 Scheduling contract

- Capture scheduler wiring only as far as this gate requires.
- Polling interval <= 1 hour.
- Capture window overlap >= 2 hours.
- Retry policy is defined per source in `config/sources/*.yaml`. No silent
  retries that rewrite history.

### G0-A.6 Fail closed

If source identity, timestamp interpretation, storage identity, or any other
required property cannot be established per the spec:

- do not guess;
- do not silently coerce;
- do not use fuzzy matching;
- record the failure explicitly;
- preserve enough metadata to diagnose it WITHOUT committing provider payload.

### G0-A.7 SECOND_RUN_IDEMPOTENT

A second ingest of already-captured objects MUST produce zero unintended state
changes. This is verified as a gate (G0-A2), not asserted.

### G0-A.8 CAPTURE_WINDOW_COMPLETE

`CAPTURE_WINDOW_COMPLETE` is reached only when 5 trading days are captured with
daily rescan (previous 24h, keyed by publication_timestamp) and 7-day rolling
rescan operating, with no unexplained gaps. This is an OPERATIONAL verification
(G0-A3) that is opened only after the scheduled runs have accrued evidence. It
MUST NOT be asserted from a single smoke run.

`es_legal_issuer_v1` (frozen):

- instrument MiFIR ID = CRPB (corporate bonds);
- issuer LEI from FIRDS RTS 23 field 5;
- GLEIF LegalJurisdiction.country = ES;
- NO ISIN-prefix heuristics.

Branches: INCLUDE / EXCLUDE / QUARANTINE / CONFLICT. Missing issuer LEI,
unresolvable LegalJurisdiction, or identity conflict QUARANTINE or CONFLICT.

## §4 G0-C — Normalization

Raw -> normalized transformation performing: lossless field preservation,
RTS 2 field mapping, price notation, quantity/notional sanity checks, exact
timestamp handling. Raw -> normalized -> ledger must be reproducible.

---

## §5 G0-D — Lifecycle reconstruction

Deferral state, partial publication, amendment, cancellation and supersession
chain reconstruction; source-exact duplicate detection and economic-duplicate
candidate flagging. No deletion ever. `NO_HEURISTIC_DELETION` enforced.
Ledger is append-only with explicit `supersedes_source_report_id` links.

---

## §6 G0-E — Cross-source market evidence

Cross-source metrics (unique ISINs, trades, intersections, source-exclusive
sets, notional/trades by source) WITHOUT coverage claims.
`COVERAGE_MEASURED` report must exist; `NO_COVERAGE_CLAIM` holds (no
completeness language anywhere). We measure observed fragmentation; we never
claim completeness we cannot demonstrate.

## §7 G0-L — Legal / ToU classification

Snapshot source terms of use for BME APA and Bloomberg APAE, and classify the
legal status of every output artifact class under:

- LOCAL_ARCHIVAL
- FREE_DELAYED_REDISTRIBUTION
- HISTORICAL_ARCHIVE_REPUBLICATION

(PASS | FAIL | UNRESOLVED). UNRESOLVED is an acceptable recorded outcome.
`SOURCE_TERMS_SNAPSHOTTED` required for 2/2 sources. Artifacts live in
`docs/legal/` and the classification table in `evidence/g0-l1/`. G0-L1 may run
in parallel with G0-A1.

## §8 Repo hygiene (cross-cutting)

- Provider payloads live ONLY in the configured local data directory (`data/`,
  gitignored). The repository holds code, schemas, tests, manifests, hashes,
  counts, timestamps, sanitized logs, and documentation.
- Evidence is metadata, never payload. `evidence/` contains manifests, SHA-256,
  counts, timestamps, logs — not provider file contents.
- CI runs deterministic, offline, fixture-based tests ONLY. CI MUST NOT make
  network requests to any provider.
- Acquisition runs locally (operator / scheduled), never in CI.
- Raw is immutable; SHA-256 recorded at capture; re-runs must not alter raw.

## §9 G0 PASS evaluation

G0 PASS requires ALL criteria in §1–§8. No partial credit, no gate
substitution. All of: acquisition (G0-A), universe (G0-B), normalization
(G0-C), lifecycle (G0-D), cross-source evidence (G0-E), and legal
classification (G0-L) must be satisfied with evidence.
